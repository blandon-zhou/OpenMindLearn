# OpenMindLearn ChatBox 式分支对话 UI PRD（2026-04-06）

## 1. 背景

当前 OpenMindLearn 的核心交互是“画布上的知识节点扩展”。这套方式适合做知识网络整理，但在连续追问、回看上下文、切换分支时，用户仍然要频繁在画布上找节点、找连线、找父子关系。

用户希望新增一套类似 ChatBox 的对话 UI：可以像聊天工具一样连续提问、查看回答，并且支持基于某一轮回答继续分叉。

本功能的本质不是再造一套独立聊天系统，而是为现有节点图谱提供第二种主视图，让“对话式探索”与“画布式整理”共用同一份数据。

## 2. 目标

1. 支持以聊天流形式查看某条知识探索链路。
2. 支持从任意历史轮次继续提问，形成清晰的分支。
3. 支持在 Chat 视图与 Canvas 视图之间双向跳转。
4. 保持现有 `.oml`、节点生成、上下文传递能力的主体兼容。
5. 降低用户在“连续问答”场景中的操作成本，同时保留画布整理能力。

## 3. 非目标

1. 本期不替代现有 Canvas 视图，Canvas 仍然是知识图谱总览与空间整理的主载体。
2. 本期不引入多人协作、在线同步、云端会话。
3. 本期不把产品改造成通用大模型聊天工具，仍以“知识节点沉淀”为目标。
4. 本期不重做 LLM 能力边界，仍沿用现有生成、扩展、上下文链路。

## 4. 核心设计原则

### 4.1 单一数据源

ChatBox UI 不是新的数据模型。底层仍以现有 `Node`、`parentIds`、`.oml` 为核心存储结构。

### 4.2 对话视图是图谱视图的投影

Chat 里看到的每一轮回答，本质上仍是一个知识节点。聊天分支只是节点关系的一种线性化展示方式。

### 4.3 分支要清晰，但不能破坏图谱能力

Canvas 允许多父上下文和跨分支引用；Chat 视图需要可阅读的单链主线。因此需要在“图谱关系”和“对话展示关系”之间建立轻量桥接。

### 4.4 用户可以在两种认知模式间切换

- Chat 模式适合连续追问、阅读、分叉。
- Canvas 模式适合总览、归类、区域整理、跨链连接。

### 4.5 兼容优先

优先复用现有接口、存储、上下文构建逻辑。V1 默认不为了 Chat 视图单独修改 `.oml` 结构。

## 5. 用户问题定义

当前主要痛点：

1. 连续提问时，用户必须在画布上反复定位“当前节点”。
2. 分支一多后，画布阅读成本迅速上升，不适合纯对话式探索。
3. 用户很难像聊天工具那样沿着一条链快速上下回看。
4. 历史回答继续追问时，虽然数据结构已经支持，但缺少清晰的“分支会话”呈现。

## 6. 目标用户场景

### 场景 A：连续学习追问

用户从一个首节点开始，连续追问 5 到 10 轮，希望像聊天一样自然向下阅读，而不是每轮都在画布里找新节点。

补充说明：

1. 如果是新建空白画布，用户可以直接进入 Chat 模式开始提问。
2. 第一条用户输入会直接触发首个节点创建。
3. 这个首节点既是图谱中的第一个知识节点，也是这条对话分支的首轮回答。

### 场景 B：从历史回答分叉

用户看到第 3 轮回答后，想从这里问另一个角度的问题，系统应能保留原链路，同时生成新的分支链路。

### 场景 C：对话后回到图谱整理

用户在 Chat 模式完成一段探索后，希望一键回到 Canvas 查看整个知识结构，并继续拖拽、分组、加标签和区域。

## 7. 功能方案

### 7.1 视图模式

新增三种工作模式：

1. `Canvas`：现有模式，保持不变。
2. `Chat`：聚焦单条分支的聊天流视图。
3. `Split`：左侧聊天流，右侧小型画布或节点详情，便于边聊边定位图谱。

默认仍进入 `Canvas`，避免打断现有用户习惯。

对于新建空白画布，应支持用户直接切入 `Chat` 模式开始首轮对话。

### 7.2 入口设计

用户可通过以下方式进入 Chat 视图：

1. 顶部工具栏新增“Chat”切换按钮。
2. 在节点右键菜单新增“在对话视图中打开此分支”。
3. 在详情面板新增“继续以对话方式探索”按钮。

进入 Chat 后，系统以“选中节点所在链路”作为当前活动分支。

### 7.3 Chat 视图布局

建议布局：

1. 左侧：分支导航区
 - 显示当前分支路径、兄弟分支数量、可切换历史分叉点。
 - 形式可参考“面包屑 + 分支计数 + 历史轮次节点列表”。
2. 中间：消息流主区域
 - 按时间和父子链路顺序显示消息。
 - 每一轮包含“用户问题 + 助手回答”两段。
3. 底部：输入区
 - 用于继续追问、上传图片、附加文件、选择扩展模式。
4. 右侧可选：上下文/节点信息抽屉
 - 显示当前回答对应的标签、备注、来源片段、附加上下文节点。

### 7.4 消息模型映射

为了复用现有节点结构，Chat 视图采用如下映射：

1. 一条“用户消息”对应节点的 `question`。
2. 一条“助手消息”对应节点的 `content` 与 `thinking`。
3. 首节点若来自“直接粘贴文本创建”，默认视为一条 `assistant seed message`。
4. 首节点若来自“prompt 生成”，则可展示为：
 - 用户消息：首轮 prompt
 - 助手消息：首节点内容

这意味着 Chat 流是对节点链的成对展示，而不是单独保存消息数组。

只要选定某个分支终点节点，并按主链规则向上回溯，就可以完整还原这条分支的 messages 流：

1. 每个节点贡献一组 `question -> content/thinking`。
2. 按父子顺序串联后，即得到完整对话记录。
3. 因此 V1 不需要额外维护 `messages[]` 持久化结构。

### 7.5 分支规则

#### 基础规则

1. 任意一条助手回答都可以继续追问。
2. 对同一父回答发起多个追问时，形成兄弟分支。
3. 当前 Chat 视图一次只聚焦一条活动分支，但用户可切换到同层其他分支。

#### 展示规则

1. 当前活动链完整展开。
2. 非活动兄弟分支收起显示为“还有 N 个分支”。
3. 点击历史轮次上的分支标记后，切换活动分支并刷新消息流。

#### 重要约束：多父节点兼容

当前系统已支持 `parentIds` 多父链与手动混选上下文，这与纯树形聊天并不完全一致。

本期不新增持久化字段，改为采用展示约定：

1. `parentIds` 继续表示该节点生成时实际依赖的全部上下文父节点。
2. Chat 主链只认“发起追问的那个父节点”。
3. 额外手动勾选的上下文节点只作为辅助上下文，不参与 Chat 主链展示。
4. 若节点存在多个 `parentIds`，默认取 `parentIds[0]` 作为展示父节点。

这要求实现层遵守一个简单约定：

1. 创建新节点时，把“真正被追问的父节点”放在 `parentIds` 第一位。
2. 其他补充上下文节点按附加上下文追加在后面。

这样可以同时满足：

1. 图谱层保留多父上下文能力。
2. Chat 层保留单链可读性。
3. `.oml` 无需为 Chat 视图单独演进。

### 7.6 对话输入能力

Chat 输入区需支持：

1. 普通追问输入。
2. 直接展开 / 针对性提问 / 自定义上下文展开。
3. 图片附加。
4. 通用文件附加。
5. 上下文选择入口。

这部分尽量复用现有扩展流程与设置项，不新增第二套 prompt 配置。

### 7.7 消息操作

每条助手消息支持以下操作：

1. 继续追问
2. 从此处分支
3. 在画布中定位
4. 打开节点详情
5. 复制内容
6. 导出 Markdown

每条用户消息支持：

1. 重新编辑并重新生成
2. 基于此问题再生成一个兄弟回答

其中“重新生成”建议实现为“创建同父节点下的新兄弟回答”，而不是覆盖旧内容，避免破坏知识演化历史。

### 7.8 Chat 与 Canvas 联动

#### 从 Chat 到 Canvas

1. 点击“在画布中定位”，自动居中到当前回答节点。
2. 切换到 `Split` 或 `Canvas` 时，保留当前活动节点选中状态。

#### 从 Canvas 到 Chat

1. 选中任意节点后可直接切到该节点所在分支的 Chat 视图。
2. 若该节点存在多个父节点，优先基于 `parentIds[0]` 回溯主链。

### 7.9 历史与草稿

建议保留以下本地状态：

1. 当前活动分支末尾节点 ID
2. 当前 Chat 输入草稿
3. 当前 Chat 模式下是否展开额外上下文抽屉

这些状态可先仅保存在前端本地草稿中，不强制写入 `.oml`。

### 7.10 默认分支判定

由于一个 `.oml` 天然是多分支全景图，本期不定义“主线”概念。

Chat 视图默认打开规则建议为：

1. 若用户是从某个节点进入 Chat，则以该节点回溯出的链路为当前分支。
2. 若用户直接从工具栏进入 Chat，则默认选择“最新对话节点”所在链路。
3. “最新对话节点”优先按节点 `updatedAt` 判定，缺失时回退到 `createdAt`。
4. 若存在并列，再以节点创建顺序或节点 ID 作为稳定兜底排序。

这样就不需要在 `.oml` 中额外持久化“当前主线”。

## 8. 数据结构设计

### 8.1 节点模型约定

本期不新增持久化字段，直接复用现有节点模型：

1. `question` 表示用户在这一轮的提问。
2. `content` / `thinking` 表示这一轮的回答。
3. `parentIds[0]` 约定为 Chat 主链父节点。
4. `parentIds[1..n]` 视为补充上下文来源。
5. `createdAt` / `updatedAt` 用于默认分支与最近对话判断。

### 8.2 前端派生结构

前端可新增派生结构，不要求直接持久化：

```ts
interface ConversationTurn {
  nodeId: string
  userMessage?: string
  assistantMessage: string
  thinking?: string
  parentNodeId?: string
  siblingCount: number
  isActiveBranch: boolean
}
```

该结构仅作为 Chat UI 渲染层数据。

## 9. 交互流程

### 9.1 从首节点开始聊天

1. 用户创建首节点。
2. 用户切换到 Chat 视图。
3. 系统根据首节点构建首轮消息。
4. 用户在底部输入框继续追问。
5. 后端返回新节点，前端将其追加到当前活动分支末尾。

对于空白画布，还应支持更直接的变体流程：

1. 用户新建空白图谱后直接进入 Chat 视图。
2. 用户输入第一句提问。
3. 系统调用首节点生成接口并创建第一个节点。
4. 前端立即以该节点渲染第一组消息：
 - 用户消息：第一句提问
 - 助手消息：首节点回答
5. 后续轮次与普通 Chat 追问流程一致。

### 9.2 从历史轮次分叉

1. 用户在第 N 轮回答点击“从此处分支”。
2. 输入新的追问。
3. 系统创建一个新节点：
 - 第一个 `parentId` 指向当前被分叉的回答节点
 - 若有额外上下文，再把其他节点追加到后续 `parentIds`
4. 当前活动分支切换到新分支。

### 9.3 混合上下文生成

1. 用户在 Chat 里发起追问时，打开上下文选择器。
2. 选择额外节点作为补充上下文。
3. 系统仍将这些节点写入 `parentIds` 或请求中的 `selectedNodeIds`。
4. 但 Chat 视图主链只依据 `parentIds[0]` 呈现。

## 10. 接口设计建议

### 10.1 可复用现有接口

现有接口基本够用：

1. `POST /api/nodes/generate`
2. `POST /api/nodes/expand`
3. `POST /api/files/save`
4. `POST /api/files/load`

其中 Chat 继续追问本质上仍是 `expand`。

### 10.2 建议的小幅协议约定

`/api/nodes/expand` 本期不必新增字段，但要明确一个顺序约定：

1. `parentId` 是本轮真正发起追问的节点。
2. 若存在 `selectedNodeIds`，返回或落盘时应保证发起追问的那个父节点排在 `parentIds[0]`。
3. 其他补充上下文节点排在后面。

这样前端在重新加载 `.oml` 后，仍可稳定派生出 Chat 主链。

## 11. 前端模块改造建议

建议新增模块：

1. `components/chat/ChatShell.tsx`
2. `components/chat/ConversationList.tsx`
3. `components/chat/ConversationTurn.tsx`
4. `components/chat/ChatComposer.tsx`
5. `components/chat/BranchSwitcher.tsx`
6. `hooks/useConversationView.ts`
7. `stores/chatViewStore.ts`

职责划分：

1. `useConversationView`：从 `nodes` 派生活动分支、兄弟分支、可渲染消息流。
2. `chatViewStore`：记录当前视图模式、活动节点、输入草稿、分支切换状态。
3. Chat 组件层只负责 UI 呈现与交互触发。

## 12. 分期方案

### V1

1. 支持从节点进入 Chat 视图。
2. 支持按单条分支渲染消息流。
3. 支持继续追问与历史节点分叉。
4. 支持 Chat/Canvas 双向定位。
5. 不改 `.oml` 结构，仍能基于现有节点数据恢复 Chat 分支视图。

### V2

1. 支持 `Split` 双栏模式。
2. 支持兄弟分支并排预览。
3. 支持对话级搜索和命中跳转。
4. 支持消息折叠、长回答目录导航。

### V3

1. 支持基于 Region 或标签启动临时对话上下文。
2. 支持对话摘要、分支命名、分支比较。

## 13. 验收标准

1. 用户可以从任意节点打开对应的 Chat 分支视图。
2. 用户可以在 Chat 中连续提问至少 10 轮，无需回到 Canvas 才能继续。
3. 用户可以从任意历史回答创建新分支，并在 UI 中明确区分。
4. 用户可以从 Chat 快速定位到 Canvas 中的对应节点。
5. 保存为 `.oml` 后重新加载，分支展示关系仍可由现有节点关系派生出来。
6. 旧 `.oml` 文件加载后仍能正常使用 Chat 视图。
7. 新建空白画布后，用户可直接在 Chat 模式输入第一句并生成首节点。
8. 给定某个分支末尾节点，系统可以仅基于现有节点数据完整还原该分支的 messages 流。

## 14. 风险与决策点

### 风险 1：多父节点与树形聊天天然冲突

解决建议：

1. 不新增持久化字段。
2. 约定 `parentIds[0]` 为对话主链父节点。
3. 图谱关系与聊天展示关系分层处理。

### 风险 2：首节点来源不统一

当前首节点既可能来自粘贴内容，也可能来自 prompt 生成。

解决建议：

1. V1 允许首节点显示为“assistant seed message”。
2. 不强求所有会话都严格从“用户消息”开始。

### 风险 3：Chat 与 Canvas 功能重复导致复杂度上升

解决建议：

1. 明确 Chat 负责“连续探索”。
2. 明确 Canvas 负责“总览整理”。
3. 避免在 Chat 中复制全部区域管理、布局编辑能力。

## 15. 推荐实施顺序

1. 先补派生规则：最新节点判定、`parentIds[0]` 主链约定、活动分支推导。
2. 再做渲染层：活动分支推导、兄弟分支切换。
3. 再接入交互层：继续追问、历史分叉、回到画布定位。
4. 最后做增强项：Split 模式、上下文抽屉、搜索与预览。

## 16. 结论

这次新增功能建议定义为：

“在现有知识图谱之上，新增一套 ChatBox 式分支对话视图，让用户可以按对话方式连续探索知识，同时与 Canvas 视图保持同一数据源、双向联动和可持久化分支关系。”

这样做的收益是：

1. 对用户而言，连续问答体验接近聊天工具。
2. 对系统而言，不需要维护两套割裂的数据结构。
3. 对后续演进而言，可以逐步从“画布产品”扩展为“画布 + 分支对话”的双模态知识探索工具。
